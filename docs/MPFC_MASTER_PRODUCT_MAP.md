## 0. Як користуватися картою

- **[БАЗА]** — зафіксовано в попередньому архітектурному аудиті; актуальність перевіряти.
- **[УЗГОДЖЕНО]** — бажана поведінка погоджена в обговоренні, не означає реалізацію.
- **[ПЛАН]** — запропонована функція, потребує деталізації.
- **[РОЗРОБКА]** — є відомості про роботу, поточний стан перевіряти.
- **[ПЕРЕВІРЕНО]** — лише після конкретного smoke-тесту з датою та результатом.
- **[БЛОКЕР]** — бракує даних, рішення або технічної основи.

**Правило оновлення:** кожна нова ідея отримує ID, опис сценарію, залежності, критерії приймання, статус і дату. Після реалізації вказувати посилання на файли/коміт і перевірку. Не підміняти «узгоджено» на «зроблено» без перевірки. Не стирати попередні рішення без запису причини зміни.

## 1. Мета продукту і шлях користувача

MPFC — платформа для створення, конструювання, розрахунку, погодження й підготовки меблів до виробництва з бібліотеками матеріалів, фурнітури, технологічних правил і асистентом.

**Цільовий сценарій:** реєстрація → компанія/тариф/права → «Прорахувати меблі» → тип меблів (перший пріоритет: кухня) → кімната та габарити → розміщення модулів → фасади, шухляди, матеріали, фурнітура → автоматичні технічні правила → 3D → BOM/розкрій/кошторис → погодження → закупівля/резерви → виробничі документи. Це **цільова карта**, а не перелік уже готових екранів.

**Принципи:** мінімум ручних технічних операцій; система рекомендує, людина підтверджує або обирає альтернативу; зміни перераховують залежні сутності; невідомі технічні дані не вигадуються; проєкти й склади різних компаній ізольовані.

## 4.1. MNT-002 — Керування монтажним вузлом після створення

**Сценарій:** користувач помилково вибрав неправильну систему кріплення під час створення монтажного вузла. Після створення він має виправити параметр редагуванням або безпечно видалити помилково створений вузол.

**Функціональність:**
1. У картці або інтерфейсі монтажного вузла доступна дія «Видалити монтажний вузол».
2. Перед видаленням система запитує підтвердження користувача.
3. Перед реалізацією потрібно перевірити залежності монтажного вузла та правила безпечного видалення, щоб не пошкодити пов’язані дані.
4. Під час редагування існуючого вузла користувач може змінити той самий параметр системи кріплення, який доступний під час створення.
5. Доступні лише значення, які реально підтримує поточна модель даних: площина, торець, перпендикулярні площини та інші наявні значення; нові значення не вигадувати.
6. Після збереження нове значення має зберігатися і відображатися при повторному відкритті вузла.

**Критерії приймання:** існуючий монтажний вузол можна безпечно видалити через UI; перед видаленням є підтвердження; при редагуванні можна змінити систему кріплення; доступні тільки реально підтримувані системою значення; зміна зберігається після повторного відкриття; існуюче редагування інших параметрів не ламається; пов’язані дані не пошкоджуються.

**Рішення / журнал рішень (перевірено 10.10.2026):**
- Спосіб з’єднання можна змінювати безпосередньо в редакторі монтажного вузла.
- Використовується існуючий `mounting_variant_key` і поточний PATCH flow.
- UI показує окрему помітну картку «Спосіб з’єднання деталей».
- Видалення доступне для вузлів із актуальним `can_delete`.
- Перед фізичним DELETE виконується dependency-check.
- Видалення блокується, якщо вузол використовується у схемах або правилах.
- Підтвердження видалення реалізоване через React modal.
- Фізичне видалення є незворотним.

**Залежності:** монтажні вузли; модель даних монтажного вузла; UI створення/редагування монтажного вузла; механізм безпечного видалення та пов’язані записи.
## 4. FUR-020 — Профільні системи та кольорові виконання

**Сценарій:** у кухні встановлено верхній L-профіль певного виробника/серії/кольору. Користувач додає C-профіль між шухлядами. Система рекомендує сумісний профіль тієї самої серії та покриття, але дозволяє вибрати інший артикул/виробника після перевірки.

**Модель:** виробник → серія → роль профілю (верхній L, середній C, вертикальний, стикувальний тощо) → технічна геометрія → кольорове/поверхневе виконання → комерційний артикул → постачальник/ціна/склад. Приклади назв FBR та Schill у бесіді умовні; конкретні каталоги й артикули необхідно звірити.

**Правила:**
1. Одна технічна геометрія може мати кілька кольорів, якщо виробник підтверджує однакові монтажні параметри.
2. Зберігати код кольору/покриття виробника, а не лише «чорний» чи «срібний».
3. Підбір за замовчуванням: той самий виробник, сумісна серія, роль і покриття; альтернативи показувати окремо.
4. Різні виробники можуть комбінуватися за рішенням користувача, але геометричну й монтажну сумісність перевіряти незалежно від схожості кольорів.
5. Якщо користувач підтвердив збіг відтінків на власний розсуд, зберегти це як локальне рішення компанії, **не** як глобально доведений технічний факт.
6. Для кожної системи: креслення перерізу, відступи, вирізи в стійках, кріплення, заглушки, фасадні зазори, 3D, правила стикування через кілька модулів.
7. Розрахунок: потрібні чистові довжини, пропил, припуски, хлисти, відрізки, відходи, фактичні закупівельні одиниці.

**Критерії приймання:** заміна кольору без зміни геометрії там, де вона однакова; заміна виробника запускає перевірку й перерахунок; відсутні технічні дані блокують автоматичне затвердження; BOM і 3D відповідають вибраному артикулу.

## 5. MOD-001 / RULE-001 — Автоматична перебудова модулів

**Приклад:** голосом або через UI: «У третьому модулі зроби три шухляди: одну нижню і дві верхні; постав середній профіль». Система визначає модуль, пропонує схему, бере рекомендований профіль поточної кухні, перераховує фасади, корпуси шухляд, напрямні, вирізи, кріплення, 3D, BOM і кошторис.

- Висоту системи шухляд вибирати з **реальних сумісних** типорозмірів, а не довільно зменшувати.
- Перевіряти висоту отворів, технологічні зазори, зіткнення, монтажну документацію, допустимі навантаження (за наявності даних).
- Зміна профілю прибирає лише попередні **автоматично створені** операції; ручні правки користувача зберігаються або вимагають явного погодження конфлікту.
- Для всієї лінії кухні враховувати суцільні профілі через сусідні модулі, стики й торці.
- Користувач бачить рекомендовану конфігурацію, альтернативи й наслідки вибору; підтвердження перед зміною виробничих даних.
- Розрахунковий рушій перевіряє технічну коректність; AI лише інтерпретує намір і пояснює результат.

**Критерії приймання:** однакова операція з UI, тексту й голосу дає однаковий розрахунок; несумісна конфігурація не видається за готову; є можливість скасувати/порівняти зміни.

## 6. STOCK-001 / STOCK-002 / CUT-001 — Склад, розкрій, резервування

**Модель залишку:** компанія, склад, фізичний ID відрізка, артикул/покриття, довжина мм, кількість, стан, джерело, партія (за потреби), резерв, проєкт, історія рухів. Два відрізки 650 і 400 мм не є одним суцільним 1050 мм.

**UI:** у виборі профілю — список придатних залишків із довжиною, доступністю, резервом і попереднім результатом розкрою. Система рекомендує, але користувач сам обирає конкретний відрізок. Приклад: потрібні 900 мм, доступні 1800 і 1900 мм; для наступного проєкту може бути важливо зберегти 1900 мм цілим. Пропил і технологічні припуски враховувати окремо.

**Стани:** вільний → зарезервований за проєктом → виданий у роботу → використаний/розкроєний; також звільнення резерву, повернення, коригування. Резервування **не дорівнює** фізичному списанню.

**Багатокористувацька безпека:** одна компанія — спільний склад; одночасний резерв одного фізичного відрізка дозволено лише одному запиту (серверна атомарна перевірка). Інші бачать резерв і, за правами, відповідального/замовлення. Резерв не повинен автоматично зникати з підтвердженого виробничого замовлення. Для чернеток — нагадування про закінчення терміну.

**Фінанси:** складський відрізок може вимагати 0 грн **нової закупівлі**, але має облікову собівартість. Кошторис окремо показує собівартість, закупівельну потребу й джерело кожної позиції.

**Критерії приймання:** два менеджери не можуть зарезервувати один відрізок; скасування повертає доступність; після різання новий залишок має правильну довжину з урахуванням пропилу; історія операцій не губиться.

## 7. Каталоги, технічні правила, постачальники

- Матеріали: canonical item + supplier offers, одиниці лист/м²/пог. м, порівняння й конфлікти, крайка.
- Фурнітура: товарна позиція відокремлена від технічної моделі, виробник/серія/варіант/комплектність/ціна.
- Монтажні вузли: склад вузла, отвори, сторона деталі, глибина, діаметр, положення, 2D/3D preview.
- Майбутня студія правил: технічні PDF/CAD/інструкції → витяг даних → перевірка людиною → тест → публікація версії. Не публікувати неперевірені AI-припущення.
- Кожен проєкт має зберігати версію використаних технічних правил і важливих цінових припущень.

## 8. 3D, кімната, меблі, виробництво

- Кімната: стіни, прорізи, розміри, перешкоди, розміщення кухонних модулів.
- Модулі: параметричні корпуси, полиці, фасади, шухляди, техніка, кріплення; команди переміщення/зміни розмірів.
- 3D: вибір модуля, обертання, приховування інших, відкривання фасадів; надалі — перевірена кінематика фурнітури.
- Виробничий ланцюг: деталі → крайка → отвори/пази/вирізи → BOM → розкрій → кошторис → креслення/експорт.
- Для першої повної реалізації: **один перевірений кухонний модуль від параметрів до виробничого результату**, потім розширення на типи модулів.

## 9. AI-001 — Асистент MPFC

**Погоджений UX v1:** плаваючий персонаж зі статичних PNG станів, текстова кнопка (тихо) та мікрофон (із озвученням); жіночий/чоловічий варіант; коротка bubble-відповідь. Анімація персонажа — пізніша версія.

**Команди:** відкриття розділів, виділення/обертання 3D, зміна полиць/техніки, створення/зміна модулів, добір фурнітури. Голосова команда з wake-word «Асистент»; складні дії уточнюються до виконання. Невідомі фрази збирати для аналізу. Асистент працює лише з доступними користувачеві даними компанії.

**Ризики/перевірки:** стабільність мікрофона, безперервне слухання, перезапуск після onEnd, TTS у voice mode, відсутність TTS у text mode, коректність виконання дій. Наявність цих можливостей у плані не означає, що регресії вже усунено.

## 10. Інтерфейс і операційна робота

- Єдиний візуальний стиль WorkspacePage; вибір фурнітури, 3D, схема, параметри; адаптивність для телефону й планшета.
- Product Center — основний інструмент запуску сервісів, перегляду логів, карти продукту, Git і БД.
- Перед зміною: діагностика → одна мінімальна правка → build → ручний smoke → лише після нього commit/push.
- Ризикові операції БД, резервів і Git — тільки з перевіркою, журналом і можливістю відновлення.

## 15. Синхронізація між Git і ChatGPT

**Основна редагована версія:** `docs/MPFC_MASTER_PRODUCT_MAP.md` у локальному репозиторії після додавання. **Для інших чатів проєкту ChatGPT:** додати актуальну копію до файлів проєкту «Калькулятор». Копії **не синхронізуються автоматично**: після суттєвого оновлення замінювати вкладення в проєкті. Нові чати мають орієнтуватися на останню дату/версію документа, але перед твердженням «реалізовано» перевіряти код і runtime.

**Безпека:** цей документ не змінює БД, код, сервер, складські резерви чи Git сам по собі.
